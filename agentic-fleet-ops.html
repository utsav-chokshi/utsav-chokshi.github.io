ROBOTICS · FLEET OPERATIONS · SIMULATION

Agentic Robotics Fleet Operations Center

A local, reproducible portfolio project for monitoring a simulated warehouse robot fleet, detecting incidents, and helping an operator investigate them safely.

Current statusThe simulator, telemetry pipeline, deterministic incident detection, investigation service, local dashboard, and one operator-approved simulation-only recovery action are implemented.
View repository ↗

01 / PROJECT GOAL

Make fleet incidents easier to investigate

The MVP simulates a small warehouse fleet and reproducible operational faults. It validates and stores telemetry, detects incidents with deterministic rules, and gives an operator a dashboard for fleet status and incident history.

An investigation service gathers evidence and returns recommendations. Any recovery demonstration is a separate step that requires explicit operator approval.

02 / IMPLEMENTED

What works today

  • Repeatable simulator: three simulated robots, seeded initial state, and selectable low battery, blocked route, disconnected robot, stalled mission, and abnormal sensor scenarios.
  • Telemetry and detection: validated telemetry is persisted; five deterministic rules detect incidents and prevent duplicate active incidents.
  • Evidence-backed investigation: the investigation service stores reports with facts separated from hypotheses and recommendations. Its tools are read-only.
  • Operator dashboard: a local Streamlit dashboard presents fleet status, incident history, investigation evidence, and recovery audit history.
  • Guarded recovery demonstration: for an active disconnected-robot incident, an operator can request a simulated reconnect, explicitly approve or reject it, and review the audit trail. The simulator action endpoint is only reachable inside the Compose network.

03 / TECHNICAL DESIGN

Local by design

The current workflow runs with Docker Compose and does not depend on a language model, paid API, paid cloud service, or physical robot. The backend exposes health, telemetry, incident, investigation, and recovery-request APIs. SQLite data lives in a Docker-managed volume.

Agreed direction, not claimed as implemented here: ROS 2 Jazzy, Gazebo Harmonic, and rclpy are part of the intended technology direction. A local language model may be evaluated later as an optional, replaceable provider.

04 / SAFETY BOUNDARIES

Recommendations stay separate from actions

  • The system does not connect to or control physical robots.
  • Investigation tools are read-only; recommendations do not approve or execute actions.
  • Only allowlisted, simulation-only recovery demonstrations can be requested, and an operator must explicitly approve them.
  • Incident detection and its tests do not depend on a language model.

05 / VERIFICATION

Evidence in the repository

The repository describes 39 unit and API integration tests covering seeded fault scenarios, investigation evidence, telemetry validation, duplicate-alert prevention, and the recovery approval flow. A GitHub Actions workflow is configured to run the suite on pushes and pull requests.

These counts and workflow details are taken from the project README; they describe the documented suite and configuration, not a claim that a run was independently observed for this portfolio page.

06 / TRY IT LOCALLY

Reproduce the MVP

With Docker Desktop running with the WSL 2 Linux engine, start the services from the repository root:

docker compose -f simulator/compose.yaml up --build -d
Invoke-RestMethod http://localhost:8000/healthz

Open the dashboard at http://localhost:8501. The repository README includes instructions for selecting seeded fault scenarios and running the automated suite.

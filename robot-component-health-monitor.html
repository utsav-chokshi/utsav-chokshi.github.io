01 / THE DATA PROBLEM

A score needs its measurement history

A useful component-health workflow must explain which recording produced an alert, whether the input was valid and which baseline was applied. I built the pipeline to preserve that evidence and reproduce the result after processing failures.

The source is 984 real industrial bearing test-rig recordings across four channels. This is a robotics-relevant component case study; the measurements are not robot telemetry.

02 / IMPLEMENTED ARCHITECTURE

Preserve, version, evaluate, inspect

  1. PreserveContent-addressed original measurements and immutable receipts precede projection.
  2. Project & recoverPostgreSQL records accepted input and lineage; replay works without the source directory.
  3. Publish featuresPrefect / NumPy → frozen inputs → typed Parquet and DuckDB checks.
  4. Freeze & evaluateReference-only median/MAD calibration and a sealed chronological policy.
  5. Inspect evidenceFastAPI verified readers → Streamlit trends, alerts, quality and source previews.
PythonPostgreSQL / AlembicPrefectNumPyParquet / PyArrowDuckDBFastAPIStreamlit / AltairDocker Composepytest

The dashboard has no database credentials or data-volume mounts. Every analytical request selects a registered build; source inspection separately verifies the original bytes and receipt.

04 / ENGINEERING VALIDATION

Recover without changing the experiment

  • Raw-first recovery: after a forced stop, 25 durable receipts but only 24 projections remained. Replay recovered the missing update; a second replay added zero.
  • Publication recovery: forced stops after feature, health and evaluation promotion recovered one verified registration per build.
  • Integrity checks: corrupted raw recordings, receipts and Parquet were rejected; missing files stayed unavailable. Verified restoration recovered reads.
  • Availability: a real database stop produced unavailable readiness/catalog/evidence responses; restarting PostgreSQL recovered the API without an API restart.

The final suites passed 67 core/API and five dashboard tests. Prepared source, base images and dependency caches were reused. Fresh-host acquisition/extraction, other architectures and exhaustive power-loss behavior remain unverified. Published code passed both core/API and dashboard GitHub Actions jobs.

06 / INTERPRETATION & FUTURE WORK

Keep condition scores tied to their evidence

The dataset lacks reliable per-record healthy/fault-onset labels and exact failure timing. An excursion is not a confirmed defect, and other bearings are not labeled healthy controls. Detection accuracy, false-alarm rate, warning lead time, failure probability and remaining life are unestablished. Physical amplitude scaling and source timezone remain unverified.

A guarded local investigation agent is a future enhancement. Its initial pilot did not pass evidence-grounding checks, so inference remains disabled. The next version needs a revised controller, validated citations and a new passing evaluation before integration.

07 / RUN IT YOURSELF

Reproduce the workflow with Docker

Use Linux/amd64 containers and PowerShell. No GPU, physical robot or paid API is required. Initial setup downloads dependencies; obtain, verify and manually extract the IMS source separately.

git clone https://github.com/utsav-chokshi/robot-component-health-monitor.git
cd robot-component-health-monitor
./scripts/Initialize-LocalEnvironment.ps1
docker compose up --build -d --wait dashboard

This starts an empty dashboard at http://localhost:8502 and API docs at http://localhost:8020/docs. Follow the reproduction guide to prepare IMS data and run ingestion, replay, features, calibration and frozen evaluation.
